# 0.7 M3: one repository context

Design record for issue #62, item 3, measured on this checkout, 2026-09-07.
The code baseline is main after M1, not v0.6.0: `src` and `tests` are byte-identical
to `9dc1f85fc0e06cb58b73bad6d09da4c89ee9a4d6` (#71) and the offline main ref
`f797f7282a224d6171db91d4f2a8325087e8b833` (#72); v0.6.0 differs in 54 files.
The M1 sequence is #64–#72; this branch includes through #71 and #72 adds only
changelog documentation. All paths and inclusive locators below are measured
on this checkout, including locators into historical records; historical commit
citations identify their own revisions. Older source numbering inside
`docs/design/0.7-m1-protected-tree-policy.md` and its reviews is not current source
numbering. Unqualified module names are under `src/receipt/`; test names are
under `tests/`. This proposal changes no production modules or tests.

The proposed owner is `RepositoryContext`. A verification should select its
candidate and base through that owner, then use immutable selected views. The
owner keeps the process-environment capture, one shared Git transport, authenticated object
facts, admission accounts and policy-fact stores. Moving a counter into that
owner does not make previously separate counters cumulative, and obtaining an
object from a shared cache does not waive the old caller's admission charge.

There are two important qualifications to the premise. Today the environment is
filtered afresh, not retained as one frozen mapping. Also, linkage shares six
admission totals and attribute facts; it does not share every policy cache or
either object's transport. These are measured facts, not proposed behavior.
The compatibility boundary for independently entered public snapshots needs
explicit treatment; changing the common composed path alone cannot erase it.
The shared-child proposal also deliberately changes packed-store availability:
one view may read authenticated bytes retained by Git after another view warmed
the child, where today's independent cold child refuses. D7 and the compatibility
boundary below name this correction and its separate approval gate.

## Ownership and lifecycle census

“Local” below means one selected snapshot's mutable `_SnapshotState`. “Pool”
means the union-find root reached through `work_pool.root()`. Neither is a
repository-wide singleton. A standalone policy is another owner, narrower than
either. Header facts are not authenticated payloads; ordinary content blobs are
streamed or returned, not retained in a general blob cache.

### Counter and refusal schedule

All fifteen fields in `SnapshotWork` (`snapshot.py:270–288`) stay public and
retain their charge schedules and values at matching successful/refused boundaries.
The separately gated D1/D7 behavior changes can change which boundaries are
reached; their resulting counter differences must be recorded explicitly. Six-field pool
admission order is **path bytes, attribute bytes, attribute rules, attribute
matching, content bytes, materialized bytes** (`2119–2154`). The proposed context
must own separate compatibility accounts and their admission schedule, not
replace `snapshot.work` with their sum.

| Fields | Charge boundary and retained ceiling domain |
| --- | --- |
| `tree_bytes`, `max_tree_object_bytes` | Selection seeds commit+root bytes; later cache misses consume then charge before parse/publication. Per-selection tree-byte total, per-object limit. Equal objects first reached by different selections remain separately admitted. `snapshot.py:1845–1876,1910–1913,2243–2317`. |
| `tree_entries`, `max_tree_entries_in_walk` | Per-reader cumulative visited records and maximum **single** walk, with old pre-refusal increments; cached walks still count. `snapshot.py:2320–2332,2430–2451,2453–2510`. |
| `path_bytes`, `max_path_bytes` | Per-path check before pooled admission; maximum only after admitted charge. Prefixes, duplicate requests, entries and listing iteration retain their distinct charge points. `snapshot.py:2378–2416`; `protected_tree.py:267–281,1297–1310`. |
| `ancestry_commits`, `ancestry_edges` | Candidate-local persistent counts; commit increments before load, edge bound before increment, base-reached branch before adding that node's edges. Repeated ancestry calls still charge. `snapshot.py:2603–2632`. |
| `attribute_bytes`, `attribute_rules`, `attribute_match_work` | Pooled, but source cache/admission remains per selected account. Load bytes precede parser refusal; successful parsed rules then charge; repeated matching uses D12 exact-step replay. `protected_tree.py:1095–1144,1241–1294,1702–1779`. |
| `content_bytes`, `max_content_blob_bytes` | Per-iterator count/total and per-blob checks precede contents; pooled bytes increment per streamed chunk; maximum after success. Plain `blob` does not increment these fields. `snapshot.py:1542–1639,2512–2537`. |
| `materialized_bytes`, `max_materialized_blob_bytes` | Local export total and pooled total preflight; increment for each successful write, including short writes before later failure; maximum after complete blob. `snapshot.py:2918–2931,2961–2996`. |

Constants and their public values are independently pinned in
`test_snapshot_features.py:1089–1118`. Structural depth/name size, caller blob
limits, iterator/prefix input counts, Git output/time/kill deadlines, attribute
line/state limits and fsck object/store/output/time limits also retain their
refusal sites even where they have no `SnapshotWork` field. Late-patched limits
must not be captured in the new environment record or in an import-time alias.
Do not change the existing definition-bound defaults incidentally either.

## Numbered disagreements and deciding probes

These are M3's D-list; D12 deliberately retains M1's number and meaning. Some
disagreements are required isolation, some are redundant ownership, and some
are actual mutable-state hazards. Consolidation must not erase that distinction.
“Run” identifies an executed probe recorded below. “Gate” identifies an additional
implementation acceptance test, not an executed experiment.

## Proposed context contract

The new type is `receipt.snapshot.RepositoryContext`, initially implemented in
the snapshot module to preserve late lookup of the existing process and reader
hooks. Moving it to another module is optional follow-up work, not part of the
ownership change. It is an explicit verification resource, not a global cache,
thread-local current repository or a registry indexed only by filesystem path.
An unrelated nested verification must not silently join the outer budget.

| Proposed public surface | Contract |
| --- | --- |
| `RepositoryContext.open(root, *, verify_objects=False)` | Validate/capture repository input and process environment once, perform discovery/config admission at the existing boundary, and return an unentered owner. Retain selected-safe-directory bytes and immutable provenance. No long-lived child exists yet. `open` is additive; existing functions gain no required parameters. |
| `context.select(revision="HEAD", *, expect_commit=None, expect_tree=None)` | Resolve the revision exactly once and authenticate commit/root tree before returning a frozen `TreeSnapshot` facade over an internal selected view. Expectations retain commit-before-tree order. Before entry, a temporary selection child is context-owned and closed immediately; after entry, selection uses its owned reader only at the reached base-selection barrier. Never resolve an already selected symbolic base again. |
| `context.__enter__()` / `context.__exit__(...)` | Acquire exactly one long-lived batch child and private config lifetime; final audit/cleanup completes before successful return from the outer verification. State transitions are unentered → entered → finalizing → closed, with abandonment terminal for reads. A failed open/select/startup does not leak resources. Closed contexts cannot be reopened or renewed in place. |
| `context.root`, `git_dir`, `common_dir`, `object_format`, `batch_pid`, `temporary_directory` | Read-only provenance/resource observations. No public writable environment, child, cache or account registry. `batch_pid`/temporary-directory facade properties still describe the resource actually serving that view. |
| `context.work_for(view)` | Return the registered `SnapshotWork` compatibility account, the same object exposed by `view.work`. The context owns its identity; callers retain current readable/mutable fields. Do not return aggregate counters in place of the existing account. Internal aggregate reads remain explicit and scheduled. |

No new public method is needed to authorize a foreign view, merge contexts,
issue a policy selection, or import precomputed passes. Pair operations stay on
the snapshot facade. Internal context methods perform account admission,
authenticated reads and audit; public library callers keep their existing
signatures. A selected view contains only context identity, selection identity,
resolved commit/tree/format, original revision label and an account key. It owns
no child, cache, environment dictionary or mutable link. All operational state,
including per-selection caches/admission membership, lives in context tables.

`TreeSnapshot.select(root, revision="HEAD", *, verify_objects=False,
expect_commit=None, expect_tree=None)` remains a classmethod with the same
signature, returned subclass behavior (`return cls(...)` today), expectation
timing and context-manager protocol. Its standalone facade creates an owner and
one selected view; the owner has no live process between selection and entry.
Existing `root`, `common_dir`, `work`, `batch_pid`, `temporary_directory`,
`header`, `entry`, `entries`, `blob`, `digests`, `parents`, `assert_ancestor`,
`changed_paths`, `verify_object_store`, `refuse_transforming_attributes` and
`materialize` signatures remain. Frozen equality/repr continue describing the
selected identity, not mutable counters. The private `_state` can temporarily be
a forwarding adapter for legacy instrumentation; it cannot become a second owner
or a writable route for replacing the context's account registration.

For explicit ownership, the composed control flow becomes: open context at the
old candidate-selection boundary; select candidate; enter context; select base
only if requested; call candidate ancestry at the same history boundary; request
store verification if enabled; run the existing pass schedule; exit the context;
publish the result. Append does the corresponding selection at its old boundary,
retains its full-OID and missing-base adapters and returns only after close.
Candidate/base views are registered with distinct accounts before any sharing
barrier. Opening a context must not eagerly select a base or check attributes.
The legacy selection facade still validates revision/expectation inputs at their
existing positions; it must not run eager context discovery in front of an
earlier argument refusal. A later base-selection config audit still screens
for denied settings at its old barrier. A harmless config-record difference
from the initial owner baseline is detected at finalization, not promoted into
an earlier history failure merely because the owner can compare it sooner (D2).

The logical accounting domain is recorded independently from immutable view
identity. At the old `changed_paths` linkage point, or only after ancestry reaches
base, the context checks the six old aggregate ceilings in order and activates
the pair's cumulative admission. Before activation each account remains local;
failure activates nothing. Context membership alone never changes charging.
The context can own this operation state without storing parent pointers or work
references on the selected views. A direct history helper preserves whatever
admission state its caller supplied. Tree bytes/walks/ancestry stay local even
after activation. Already activated pairs retain the old no-op behavior under a
late lowered limit until the next actual charge.

### Proposed compatibility boundary and deliberate corrections

Independent public snapshots have separate resources and failure domains.
Preserving them requires the legacy pair adapter. Existing callers can do this,
and the suite observes it:

```python
candidate = TreeSnapshot.select(root, candidate_oid)
base = TreeSnapshot.select(root, base_oid)
with candidate, base:
    candidate.assert_ancestor(base)
```

At the point ancestry is called, two independently selected environments,
config baselines, processes, entry tokens and accounts already exist. Both PIDs
are observable, their exact command sequence is pinned
(`test_snapshot_security.py:919–1054`), and their failure domains are separate
(D11/D13). Successful ancestry also causes **future** public reads on either
object to see the shared totals. Moving them into a new owner would either
rebind immutable subjects, silently discard a prior environment/audit baseline,
change child/close behavior, or require an adapter that keeps the relationship.
Renaming that adapter “context” does not retire mutable linkage. Automatic
ambient-context joining additionally couples otherwise unrelated operations.

The proposed contract has an explicit compatibility boundary: new owned verifications
use the context above; independently created legacy facade owners retain the
narrow pair adapter and their old behaviors. Borrowed helpers do not adopt or
close these owners. No automatic cross-context cache or policy-authority reuse
is permitted. The adapter is the existing admitted pair relationship, quarantined
from the new core, with the old six-counter schedule. It is not the design for
new verifications. This keeps existing consumer signatures, fakes and tests
meaningful while the composed command stops depending on mutable linkage.

This proposal achieves one context for an owned verification, but it does
**not** claim literal removal of all linkage from the supported legacy surface.
Full retirement requires resolving that compatibility conflict: migrating
callers to explicit shared selection and changing the cross-owner behavior is a
contract change requiring its own approval and consumer migration.
The plan below names the core retirement step and the separate full-retirement
gate. Under the task's unchanged-behavior requirement, retain the adapter until
that gate has an approved compatible resolution. Likewise D1's true capture-once
semantics must be identified as the requested M3 correction, not falsely reported
as matching the legacy moving-environment trace.

Two deliberate corrections are proposed for the new owned path. Neither is
approved by this design fold or covered by an “unchanged” compatibility claim:

| Correction | Observable difference and required decision |
| --- | --- |
| D1: capture-once environment | All children derive from the initial process input instead of reading later ambient non-Git changes. Preserve the ordered five-variable preflight and approve the before/after environment trace separately. |
| D7 / A7: context-scoped availability | The shared child's process-local Git packed-store state is part of the verification's resource lifetime. After A warms a pack and it is removed or replaced without the target, B may still read/hash the authentic payload; today's separately entered cold B refuses `object … is unavailable`. This can change overall PASS/refusal, phase progression, later error precedence and public counters because B now reaches admission and later work. Record those consequences in full; no new refusal wording or authentication waiver is proposed. |

Host observation recorded by M3-PR1 (#74, `tests/m3_store_expected.py`,
`HOST_CASE_TRACE`): the D7 packed-store matrix is host-dependent in one
permutation. On the macOS build host (case-insensitive APFS, Git 2.53.0) a
reader that has warmed a pack still serves the original payload after that
pack is tampered, while a cold account refuses; on the Linux CI runner
(ubuntu, Python 3.11 to 3.13) a tampered pack refuses on every account, warm
or cold. The remove and replace permutations, and every loose and duplicate
case, match across both hosts. The legacy and live legs agree on each host.
A7's admitted difference is therefore the removed-or-replaced-pack
availability on both hosts, and the tampered-pack serving only where the
platform's Git serves it; both hosts' traces are pinned per host, and the A7
gate must present its before-and-after traces for both.

The transport shape is decided here: retain one shared child, subject to the
separate A7 approval gate before ownership implementation. One context owns the
environment/provenance baseline, framed transport and its retained Git state,
account registrations, authenticated stores, policy facts and final audit.
It does not own an independent cold-process availability history for each view,
or a stable filesystem snapshot of the object store. Git need not retain every
removed object: loose-object removal refused in both warm and cold controls.
Availability means what that live child can supply at the reached request; payload
framing/type/size/hash, role, structural limits and per-account charging still
decide acceptance. No Python payload cache may substitute for a required read.

This choice preserves the issue's shared resource lifetime, one framed failure
domain and centralized ownership without claiming cold-process equivalence that
the probe disproves. The legacy pair adapter retains both independent children,
their audit baselines, availability histories and future six-counter linkage.
Unchanged-store compatibility remains mandatory for both paths. Changed-store
differences on the new owned path are admitted only by A7, with explicit old/new
traces; the gate must also demonstrate the unchanged legacy warm/cold split.
If A7 is not approved, PR2/PR3a cannot proceed under this proposal; retaining a
child per view would require a revised design rather than an implicit fallback.

### Environment, transport and authenticated caches

Capture non-Git ambient values once, including `HOME`, `PATH` and locale, before
the first context Git child. Keep that private immutable mapping distinct from
live compatibility limits. Each child receives a fresh dictionary derived from
it with the same three Git keys. Temporary config pathname may differ across
setup/selection/entry phases, so it is the only per-child environment substitution;
no second `os.environ` read is needed for it. Retain the private config contents,
0600 entered file permissions, safe-directory audit and no-includes commands.
The five-variable preflight remains at the old public boundary; its implementation
can delegate to a private checker of the captured mapping while its no-argument
public facade still checks the current environment when called independently.
Keep a replaceable call path for tests patching the public checker.

One entered context has one framed reader and one physical in-flight frame token.
Every frame fully drains/authenticates before another request. A partial frame,
callback exception, failed hash or abandoned reader marks the context abandoned
and invalidates every selection and policy it issued. Preserve old text and
close-note precedence. Do not silently start a replacement process and reuse the
old subject token. No parallel candidate/base payload reads are introduced.
Standalone fake `_BatchReader` frame tests still exercise the same class methods;
the context must not require those unit fakes to grow a subprocess or ledger.
This lifecycle includes Git's process-local pack state, not only Python's maps.
Authenticated availability from an earlier request can therefore serve another
account under the deliberate D7 correction; a second request is not a cold child.

The context stores authenticated immutable tree/commit records by object format,
OID and required role, alongside compact **per-account** admitted-object sets.
Header entries remain separate. For the first legacy miss in each account, retain
`info`/payload authentication, limit/parse/role admission and charge order, even
if another account supplied equal retained records. Only then may storage be
interned. In this ownership step, do not remove a formerly reached `consume`
merely because a sibling has seen the same OID. These calls preserve authentication
and admission, while A7 explicitly accepts the packed-store availability difference
they cannot prevent. Repeated reads already warm in that account
follow the old hit schedule. Keep content blobs streaming and materialization
writes real; neither is made free by raw-object or policy facts.

Header membership also needs logical selection-phase/entered-account scope:
today the selection child's header map disappears before entry, and two entered
children start with separate maps. A new shared child's previously seen header
must not suppress the `info` role/type request formerly reached by a cold account.
That request still uses a warm Git process; logical header isolation does not
establish independent-process availability. The physical reader can
own the maps and request machinery while the context supplies the logical scope;
the low-level fake-reader protocol remains usable without such an account.

This permits one cache owner without conflating actual retained bytes with
admitted tree bytes. Record actual child/frame counts and retained-memory counts
separately from `SnapshotWork`. Do not add an aggregate context memory ceiling
that introduces an earlier refusal; bound storage by admitted objects/paths and
compact checkpoints under existing ceilings. Release heavy stores on owner close
when no compatibility observation requires them; always revoke authority first.
Do not reset public work counters or completed-work telemetry on close. Store
verification readiness, ancestry-head evidence and attempted flags are also
registered per account; “one context” is not permission to replace the existing
once-per-snapshot facade rule with one global attempted bit. The composed path
still explicitly makes exactly one store-verification request.

### Policy identity, fact keys and substitutes

Bind `TreePolicy` once to an immutable registration consisting of context token,
selection token, resolved root/private/common directories, format, commit/tree,
account identity and policy version. Keep existing constructor arguments and the
subject/work mismatch refusal. `SubjectIdentity`'s existing session field can
hold an opaque frozen session binding carrying both tokens; no new required
constructor field is needed. `snapshot` remains the public facade but is not
the sole mutable reference from which authority is reconstructed each time.
Successful reuse validates registration, live context and live facade lease,
exact evaluator issuance, full plan fingerprint, purpose and completed stages.
`GitEntry` bindings remain selection-specific, even for two selections of the
same commit in one context; entries from base do not authorize candidate reads.

Context owns pure fact stores. Name/fold and mode primitives may share only
immutable input/version/operative-hook keys; path/ancestor facts also bind
selected tree and topology scope. Policy runs, incomplete/completed obligations,
findings with traversal positions, export selections and issuance are indexed by
selection and evaluator/plan, not by OID alone. Parsed attribute-source membership
uses selection token plus exact raw path (including negative lookups); rule
checkpoints retain the current key dimensions at
`protected_tree.py:1241–1246`. Path outcomes bind context/selection, version, raw
path and operative matcher/step/source-reader identities; plan outcomes add the
complete fingerprint. Do not merge acceptance across subjects when only a pure
fold or match was shared. Preserve weak view/selection issuance registries and
all M1 raw-topology/mode/ancestor/name/attribute scope barriers.

The reader substitution boundary stays ahead of all context-specific access.
Only an exact concrete, registered built-in reader can issue authenticated policy
views. Composition fakes continue through their old protocol with no context or
ledger requirement. Accepted binding subclasses use their entries/listing/digests
and the shared mapping algorithms, with no view/selection constructors. Preserve
declaration-before-reader refusal, empty attested input, and missing-file masking.
Directory adapters remain directory adapters. M3 adds no Git requirement to them.

For owned-composition dispatch, retain the public `TreeSnapshot.select` hook. A
private context selection binding can be passed inside the built-in implementation,
but the public call site must still honor replacements. Detect the operative
class and classmethod **against captured originals**, then use the context-aware
built-in path only when the intended implementation is still installed. If either
was substituted, retain the old composition protocol wholesale. Do not compare
`verify.TreeSnapshot` with another currently mutable module attribute and assume
identity establishes the original. Test patches on the class, on `select` itself,
before import and after successful selection. This is implementation acceptance
work, not permission to add a hidden required keyword to fake readers.

Keep corpus's existing `_VERIFY_CORPUS_BINDING_ORIGINAL` guard. When a public
binding substitute is operative, invoke it once and never bypass it by routing
directly through context policy. Independently count the built-in shared-custody
branch; equality of public verdicts alone cannot prove that branch ran. Preserve
all late parser/matcher/limit/source/writer hooks through call-time forwarding.
Do not freeze test patch configuration together with the process environment.

### Closing audit and publication

Finalization is an owner operation. It reserves the context against new reads,
abandons a remaining active stream, closes/reaps the batch, rechecks private and
common sentinels, compares complete config records against the captured baseline
under the same derived environment, reruns config policy, and cleans the private
directory regardless of failures. Preserve that order and exception notes from
`snapshot.py:2014–2081`. Mark the context terminal even on cleanup failure.
Borrowed helper/materialization exits must not close the outer context early.
Historical facade owners keep their existing close order through the adapter.

All tree-derived evidence is provisional until owner exit succeeds. Finalization
failure revokes reuse from every issued view/selection even if its stage had
completed. For composed output, keep the **actual** legacy rendering at
`verify.py:835–849`: retain an already recorded history row, remove other passes,
clear chain/corpus, fail custody and leave binding/declaration incomplete. The
retained history row is not authorization to emit an overall PASS or use closed
policy evidence. Append's return unwinds context first and still converts the
failure to `AppendError`. An existing body exception remains primary and receives
closing notes. Neither success nor a finalization-failure body should cause a
second audit through accidental nested owner `__exit__` calls.
