## 1. The two invariants and the format

`src/receipt/evidence.py:541-550` is exactly DSSE PAE: literal `DSSEv1`, one ASCII space before the decimal UTF-8 byte length of the type, one before the type, one before the decimal payload byte length, one before the payload. ASCII decimal integers produced by `str(len(...))` have no leading zeroes. `src/receipt/evidence.py:1104-1105` signs `_pae(spec.schema_version, raw)` through `sign_payload(..., domain=b"")`, whose implementation at `src/receipt/sign.py:259-286` signs exactly `domain + payload`. `_verify_records` supplies the same `_pae(spec.schema_version, raw)` to the exact-bytes verifier at `src/receipt/evidence.py:851-857`.

Independent probe used DSSE's published hello-world vector (type `http://example.com/HelloWorld`, payload `hello world`), a non-ASCII type `é` proving its length is 2 bytes rather than 1 character, and an empty-type/empty-payload vector. All matched. A small independent decoder round-tripped five cases, including embedded spaces, NUL and newline. A real emission produced a 64-byte signature accepted against framed bytes and refused against the raw record. These supplement `test_the_frame_is_the_dsse_pre_authentication_encoding` (`tests/test_evidence.py:203`), `test_the_frame_is_self_delimiting` (`:225`), and the real-signature three-way invariant test (`:134-195`).

PAE is injective in the tests' sense: `PAE("a", b"bc") != PAE("ab", b"c")`, and the signature for the former fails for the latter. Neither printable separators nor NULs embedded inside the type create ambiguity because its UTF-8 byte length determines the boundary. The public construction refuses an empty schema (`evidence.py:215-219`), even though `_pae` itself correctly handles empty bytes as the generic encoding does.

Record keys are fixed at `evidence.py:362-375`; the authorizing manifest validator has a different exact-key set. `test_an_evidence_record_is_refused_by_the_authorizing_verifier` checks the structural refusal before values, the framed signature's failure as a bare manifest signature, and its success as an evidence signature. The extra `.body.json` sidecar is another release-directory rejection route, not the core separation invariant.

### Ruling: retain the detached raw 64-byte signature sidecar

[DSSE's protocol](https://github.com/secure-systems-lab/dsse/blob/master/protocol.md) defines PAE signatures independently of storage/transmission and recommends, rather than requires, its JSON envelope. [Issue #34](https://github.com/TheAxiomFoundation/receipt/issues/34) selects the frame for new record types and explicitly retains existing manifest exact-byte signatures; its parenthetical mention of `Envelope`, `pae`, and threshold verification is an implementation reference, not a mandate to package evidence inside an envelope. [Issue #7](https://github.com/TheAxiomFoundation/receipt/issues/7) requires role separation in signed bytes, with broader typed role/key binding still deferred in its comment thread. PAE with schema-as-type provides the requested framing slice here; this PR does not claim to finish witnessing, chronology, role-specific key allocation, or rotation-as-recorded-event.

I would make the same sidecar ruling as the contributor proposes: keep the raw detached signature over PAE because the canonical payload already exists in the closed directory and the agreed/pinned schema fixes the payload type; a second base64 copy adds no invariant. Call this “DSSE PAE framing with a detached Ed25519 signature”, without claiming the files are the standard DSSE JSON envelope. The inline implementation is stdlib only and explicitly marked for replacement by #34's package primitive at `evidence.py:535-538`, meeting the maintainer's ruling.

## 2. The strict guard

The strict-input claim is incomplete. The five advertised categories are not uniformly enforced, and the accepted input set is not closed under canonical serialization followed by JSON parsing.

| Input class | Observed behavior and code |
| --- | --- |
| Integers outside ±(2**53−1) | Refused at evidence.py:483–489 before serialization when the guard is reached, including nested values. This is a conservative safe-integer policy: some excluded integers, such as 2**53, are representable exactly. canonical.py:86–94 converts all excluded integers through float, which can round or overflow. |
| Non-finite floats | Refused at 491–493. On-disk NaN/Infinity constants are already refused by parse_constant at 565–569; 1e999 gets past that parser callback and is refused by the strict walk. |
| Negative zero | Python -0.0 and parsed JSON -0.0 are refused at 494–495 before canonical.py:52–53 could fold them to 0. A textual integer -0 is also rejected, by canonical-byte equality. |
| Surrogates in string values | Any surrogate code point is refused at 497–504, including explicitly represented surrogate pairs; real astral Unicode scalars pass. This prevents canonical.py:41–42 from re-escaping/recombining those Python spellings. |
| Surrogates in object keys | **Missed:** 510–514 checks key type but only walks the value. canonical.py:107–110 sorts and serializes keys, and escapes lone surrogate keys back to the same bytes. See F1. |
| Non-string keys | Guard rejects them in bodies and the assembled producer/payload. Refs are inspected earlier, so malformed mixed keys can escape as TypeError. See F3. |
| Other finite floats | The walk permits them, but floats serialized as large integer tokens fail the next verification. See F2. |
| Other Python objects/cycles | Unsupported types are deliberately delegated to canonical.py, so tuples/bytes leave as TypeError. A cycle is traversed without an ancestor set and leaves as RecursionError; canonical.py:98–102 instead raises a deliberate ValueError. Neither produces a green record, but “everything canonical would raise on” is not a literal guarantee of this guard. |

The intended four boundary calls exist: emission body at 1082 before 1083; emission assembled payload at 1096 before schema validation/serialization at 1097–1098; parsed verification record at 591 before schema/byte checks at 592–593; parsed verification body at 821 before canonical equality/hash at 827–832. Verification's JSON decoder necessarily reads syntax/keys first and rejects duplicate keys/constants. Emission's refs validation and sorting at 1081/1092 precede the payload walk, so the stronger “before anything reads values” claim is false for refs. The standalone schema/serialization helpers themselves do not promise to call the guard.

**F1 — high, non-residual: string object keys bypass the surrogate refusal.** Location: src/receipt/evidence.py:510–514; canonical.py:41–42,107–110; missing tests at tests/test_evidence.py:1505–1520,1597–1632. With an actual generated Ed25519 key, ordinary emission of body={chr(0xD800): 1} writes an escaped U+D800 JSON key plus one LF, and public verification returns one green record. A nested list/dictionary holding a lone low-surrogate key (U+DFFF) also emits and verifies green. This is not a race, malformed signature, or unauthorized key: a stated strict-input refusal is bypassed in a signed, accepted record. An explicit surrogate-pair key likewise gets through emission, then fails canonical equality after JSON recombines it. Fix the dictionary walk to validate every string key as a string, with an unambiguous key-location label, before walking its value. Add high/low/pair key regressions at emission and independently signed body verification, including nesting. Existing surrogate tests put the surrogate in a value and cannot catch this.

**F2 — medium, non-residual: accepted finite floats can leave an unverifiable directory.** Location: src/receipt/evidence.py:491–496,815–827,1082–1083. Body {"n": 1e20} passes the guard and emission returns a record after all three files are written. canonical.py:57–61 emits the body token 100000000000000000000 with no decimal point or exponent; json.loads reconstructs an int, and verification rejects it at 483–489 as outside the safe-integer range. float(2**53) and -1e20 reproduce the same failure. The next append also runs that verifier and cannot extend this directory. Controls float(2**53−1) and 1e21 emit and verify; the latter stays an exponent-form JSON float.

This requires a consistent wire-level numeric policy, not merely another type check at verification. After serialization, an originally unsafe Python int and the equal integral float have the same bytes, so the verifier cannot both reject that int token and admit it because it used to be a float. With the current integer-token policy, the small compatible fix is to reject finite floats whose canonical spelling will parse as an out-of-range int **before any sidecar write**, and narrow the “finite floats pass” promise accordingly. Alternatively choose and document a different numeric representation/policy before publishing v1. Add positive and negative round trips at both safe-integer boundaries and the fixed/exponent formatting threshold; the current positive test uses only 0.5 for a nonzero float.

**F3 — medium, non-residual: malformed refs still bypass the named refusal vocabulary.** Location: src/receipt/evidence.py:1081,282–290,1096. Reproduced with refs=[{"kind": "record", "sha256": "a"*64, 1: 0, "extra": 0}]. _validate_ref_entries calls _exact_keys, which sorts the heterogeneous unknown-key set at 288 and raises bare TypeError ("'<' not supported between instances of 'int' and 'str'") before the payload strict guard. The new records directory remains empty, so this is a correctness/API-refusal defect, not an accepted bad record. It is the same category maintainer item 8 explicitly asked to close. Strict-check refs with the desired path prefix before structural validation, or make _exact_keys reject non-string keys without sorting heterogeneous objects, and add this mixed-key case to the refs regression battery. The existing non-string-key test covers only body and producer.

Additional independent controls passed for None, False, True, +0.0, 5e−324, safe boundary integers, and a real astral Unicode object key. These support the guard's valid cases without claiming an exhaustive numeric proof.

## 3. Emission

The actual order is:

1. Decode the immutable private-key PEM and derive its public SPKI digest (`evidence.py:879-915`, called at 1007). Compare to required construction-time `EvidenceSpec.producer_spki_sha256` (214, 1008-1011). A mismatched or unusable private key refuses before `mkdir`; `test_emission_with_an_unpinned_key_refuses_before_it_touches_disk` (1231) asserts the entire fixture directory remains empty.
2. Confinement check at 1013, then `mkdir(parents=True, exist_ok=True)` at 1014. An invalid subsequent body can leave an empty directory; the narrow claim that a *key* refusal leaves no directory is accurate, and no record/body/signature content is written yet.
3. Open the directory and acquire `flock(LOCK_EX | LOCK_NB)` at 943-946. Keep that descriptor open over the entire call to `_write_evidence_record` (1015-1026); context-manager `finally` closes it (958-959), releasing its advisory lock. The lock file is the directory inode, so no extra closed-world `.lock` entry is introduced. A separate open by another cooperating emitter conflicts; it does not wait or proceed. `EAGAIN/EWOULDBLOCK` maps to “another emitter” (948-952), every other `flock` `OSError` to “cannot hold” (953-956). Directory `os.open` errors precede this wrapper. This is a POSIX contract (`fcntl` is imported unconditionally at 115); filesystems that do not support the lock fail closed when they return an error.
4. Inside that held lock, `_verify_records` at 1067 verifies the entire existing directory, using the public half of the same signing key (1070). Its one shared implementation performs confinement/enumeration, canonical record parsing/schema/digest filename/index/predecessor checks, strict and canonical body checks/body digest, and the pinned signature check for every entry (791-873). The index and predecessor are from `verification.head` alone (1073-1079), not a separately parsed filename or unverified record.
5. Validate caller refs before sorting (1081), strict-validate and serialize body (1082-1083), assemble payload and sort refs (1084-1093), strict-validate payload and validate its schema (1096-1097), serialize/digest filename (1098-1099), reject a pre-existing record or symlink (1100-1103), sign the PAE frame with empty primitive domain (1104-1106).
6. Write body (1108), signature (1109), then exclusively create record with `O_WRONLY | O_CREAT | O_EXCL` (1113-1115), finally write record through its descriptor (1120-1121). No application-content validation takes place after the sidecar writes, but an OS write/open failure or final `FileExistsError` can of course still refuse after them. Thus “everything that can refuse [is before the first write]” at 1059-1060 is overly absolute wording.

A deterministic probe injected a regular file at the exact final `os.open` after the precheck. The final `O_EXCL` raised the translated `EvidenceRecordError` at 1116-1119 and preserved the planted file’s sentinel bytes exactly. This covers a branch the existing repeat-emission test does not reach: that test mocks empty enumeration and is already refused by the existence precheck at 1100.

## 4. Verification and confinement

For a stable checkout, `_assert_records_directory_is_confined` is sound for the stated checks: it delegates every configured record-directory component (including final component and dangling links) to `release_chain.assert_no_symlinked_state_component` (621-624; helper 1428-1459). This also binds component spellings through parent listings at 1458. It compares `realpath(records)` against `realpath(release_root)` and rejects equal/descendant paths (629-638), catching a configured release root that resolves to the otherwise unlinked evidence directory. It does not require a release root that is elsewhere to be symlink-free, which is correct for this separation question.

Enumeration first performs this same check even for absence (653-655), then requires a directory (656-659). Every enumerated entry must be a regular non-symlink (664-668); only the three exact filename grammars are admitted (669-684). Orphan bodies and signatures (686-695), duplicate indices (703-706), missing body (708-709), missing signature (710-713) all refuse; sorting by the four-digit filename establishes the traversal order (715), while verifier checks actual contiguous indices and links (799-813).

**Residual finding, high behavior impact, `residual_class: true`: `src/receipt/evidence.py:554-559,839-843`.** Both `_load_canonical_json` and signature loading check `Path.is_symlink()/is_file()` and then separately follow the path in `Path.read_bytes()`. A writer ignoring the directory lock can replace any already-approved record, body, or signature leaf with a symlink between those steps. In three deterministic independent probes, patched `Path.read_bytes` moved the approved leaf to a sibling outside the root and planted a symlink to it immediately before the real read. `verify_evidence_records` returned green with one valid record each time, and the leaf was a symlink outside the root at return. No signature forgery or malformed fixture was required. This is exactly the requested same-directory noncooperating-writer residual class, so it is not a merge blocker under the review policy.

The package's current idiom at `release_chain.py:1546-1628` is the right fix for that leaf race: component `lstat` plus exact-spelling checks, one `O_NOFOLLOW | O_NONBLOCK` open, `fstat` regular-file and `(st_dev,st_ino)` identity check against the approved leaf, then bounded reads from that descriptor. In the same deterministic injected leaf-symlink race at `os.open`, `_regular_file_bytes` refused `ReleaseChainError: required state file is missing or non-regular`. Factor/adopt that idiom for all three evidence reads, translating its refusal into `EvidenceRecordError` as appropriate. The descriptor approach also avoids a FIFO swap blocking `read_bytes`. It does not claim to lock out ancestor renames, in-place writes to the approved inode, or a writer replacing the directory inode used as the advisory lock; those remain explicit concurrent-writer residuals. Do not describe this 0.6 helper as an `openat` walk through retained directory descriptors: its code does a component `lstat` walk and opens the final path once.

The same outside-lock writer can also insert a sidecar symlink after enumeration but before `write_bytes` (1108-1109), causing those ordinary writes to follow it; the final record's `O_EXCL` does not harden sidecar writes. This has the same residual precondition and is not a separate non-residual blocker. The lock/confinement prose should qualify cooperative/static assumptions rather than promise complete race freedom.

The public zero-record result still requires a readable configured public-key file because verify_evidence_records reads it before enumeration (747–755); no record signature or SPKI comparison is performed when there are no records. An absent records directory and an existing empty directory return records=(), head=None with directory_present=False/True respectively. This is appropriate for Git's inability to track an empty directory and does not establish completeness relative to a separately expected head.

One additional scope probe put a regular file at root/evidence with records_relative="evidence/records". Verification returned the absent-directory result, because the imported spelling walk deliberately leaves ENOTDIR to its caller and Path.exists() returns false. There are no records below that file, so this is not another accepted bad record or merge blocker under the stated absence contract; distinguishing this configuration error with an ancestor lstat/type refusal would improve diagnostics and match the stricter 0.6 manifest-directory guard.

These are the exact stale or materially overbroad statements observed. Existing comments that clearly narrate an old defect as history are not themselves inaccurate.

1. **Known frame wording** — `evidence.py:21` and `:104-105`: replace `DOMAIN + raw` / `DOMAIN` followed by bytes with `PAE(schema id, record bytes)`, including the record's trailing LF. `__init__.py:25` and branch `README.md:20,30`: replace “signed under its own domain” / “signed over a domain string” with schema-typed PAE. 2. **Planting mechanisms** — `evidence.py:32-33` says three mechanisms; `:38-41` describes pre-0.5.2 behavior. At 0.6, record + body + signature fails unknown-file enumeration; record alone and record + signature both fail required witness coverage; record + signature + correctly named configured witness sidecars passes enumeration and fails manifest schema. The contributor reply calls them “four planting mechanisms”; it should say “four planting arrangements” to avoid replacing one miscount with another. 3. **Default schema** — `evidence.py:163-165` says directory, schema id and pin all arrive from consumer committed code, never defaults. `schema_version` does default to `SCHEMA_VERSION` at `:181`; the producer filename also has a default at `:182`. The order is harmless, but remove “must” and the false explanation.
10. **POSIX rationale** — `evidence.py:932-934` says the package's state reads open through directory descriptors. Current 0.6 `_regular_file_bytes` is a component `lstat` walk followed by a single path `os.open` with `O_NOFOLLOW | O_NONBLOCK`, descriptor `fstat` regular-file/inode validation, and descriptor reads (`release_chain.py:1546-1628`). Strictly, `flock` is widely available on the supported POSIX platforms rather than an operation standardized by POSIX itself.
11. **Which refusal leaves no directory** — `evidence.py:981-982` generalizes the signing-key refusal to “a refused emission leaves no directory behind”. Body/payload/schema/signature generation validations are indeed before file writes, but exclusive-create conflict is detected after both sidecar writes (`:1108-1119`), and disk IO can fail. Say that input/chain validation completes before sidecar writes, and document orphan/partial files on write failure. The competing-writer exclusive-create case is residual under the review's definition.
13. **Write/read order** — `evidence.py:1002-1004` says sidecars being written before record is “the order enumeration reads them in”. Enumeration uses unspecified `iterdir()` order, collects filenames, then verification reads record/body/signature (`:794-843`). Say the record is created after both sidecar writes; interruption before record create leaves orphans and verification fails closed. This is a residual class, not a fresh merge condition under the requested review policy.
